# Асинхронный сервис процессинга платежей

## Установка и запуск

Нужны Git, Docker, Docker Compose и Python 3 (для тестового приёмника webhook).

```bash
git clone https://github.com/meanyf/payments-processing.git
cd payments-processing
cp .env.example .env
docker compose up --build -d
python3 scripts/webhook_server.py
```

Если Docker требует `sudo`, добавьте его перед `docker compose`.
Миграции применяются автоматически.

Последняя команда запускает тестовый сервер для приёма результатов платежей. Запросы ниже выполняйте в другом терминале.

[Веб-интерфейс RabbitMQ](http://127.0.0.1:15672): логин и пароль — `payments`.

## Примеры запросов

Запросы можно выполнять через [Swagger UI](http://127.0.0.1:8000/docs) или через `curl`, как показано ниже.
В Swagger нажмите **Authorize** и введите `change-me` — API-ключ из `.env.example`.

### Создание платежа

```bash
curl -i http://127.0.0.1:8000/api/v1/payments \
  -H 'X-API-Key: change-me' \
  -H 'Idempotency-Key: test-payment-1' \
  -H 'Content-Type: application/json' \
  -d '{
    "amount": "100.00",
    "currency": "RUB",
    "description": "Тестовый платёж",
    "metadata": {},
    "webhook_url": "http://host.docker.internal:9000/webhook"
  }'
```

Ответ — `202 Accepted` с `payment_id`, `status` и `created_at`.
Для нового платежа укажите новый `Idempotency-Key`.
После обработки в терминале webhook-сервера появится JSON с `payment_id` и `status` (`succeeded` или `failed`).

### Получение платежа

Подставьте `payment_id` из ответа на создание:

```bash
curl 'http://127.0.0.1:8000/api/v1/payments/<payment_id>' \
  -H 'X-API-Key: change-me'
```

После обработки статус изменится с `pending` на `succeeded` или `failed`, а `processed_at` будет заполнен.

## Обработка платежа

1. API сохраняет платёж и событие в `outbox` одной транзакцией.
2. Publisher читает outbox и отправляет событие в очередь `payments.new`. Отметка об отправке сохраняется после подтверждения RabbitMQ.
3. Consumer получает событие, эмулирует обработку за 2–5 секунд и сохраняет результат в БД.
4. После завершения транзакции consumer отправляет HTTP POST на `webhook_url` с полями `payment_id` и `status`. Ответ `2xx` означает успешную доставку.

Результат эмуляции: 90% `succeeded`, 10% `failed`.

`CONSUMER_PREFETCH_COUNT` в `.env` ограничивает число одновременно обрабатываемых сообщений на процесс consumer; по умолчанию — 4. Значение `1` включает последовательную обработку. При увеличении лимита учитывайте пул БД: каждый активный обработчик использует до двух соединений одновременно, включая advisory lock.

### Идемпотентность

- Повторный запрос с тем же `Idempotency-Key` и теми же данными возвращает существующий платёж.
- Тот же ключ с другими данными возвращает `409 Conflict`.
- Уникальное ограничение БД защищает от создания дублей при параллельных запросах.
- Событие из `outbox` может быть доставлено повторно. Если результат платежа уже сохранён, consumer использует его без повторной эмуляции.
- Advisory lock в PostgreSQL допускает только одну активную обработку одного платежа, включая отправку webhook. Параллельный дубль возвращается в очередь без расходования попытки. Блокировка действует между процессами consumer и освобождается при завершении транзакции или закрытии соединения.
- После успешного webhook consumer сохраняет `webhook_delivered_at` перед ACK. Дубли с этой отметкой подтверждаются без отправки webhook и расходования попыток.

Если процесс упал между HTTP-доставкой и сохранением отметки, webhook может быть отправлен повторно. Получателю следует обрабатывать уведомления идемпотентно по `payment_id`.

### Повторы и DLQ

Общий лимит — три попытки: первый запуск и два повтора. Попытка учитывается с начала обработки сообщения. Ошибки и падения consumer после начала обработки расходуют попытку.

| После ошибки | Куда отправляется сообщение | Что происходит дальше |
| --- | --- | --- |
| Первая попытка | Outbox с `available_at` | Не раньше чем через 2 секунды публикуется в `payments.new` |
| Вторая попытка | Outbox с `available_at` | Не раньше чем через 4 секунды публикуется в `payments.new` |
| Третья попытка | Outbox для отправки через `payments.dlx` в `payments.dlq` | Сохраняется `exhausted`, автоматическая обработка прекращается |

Publisher раз в секунду выбирает события outbox с наступившим `available_at`. При недоступности RabbitMQ они остаются в БД; повтор публикации не расходует попытки обработки.
ACK исходному сообщению отправляется после успешного webhook либо сохранения повтора или передачи в DLQ в outbox. Состояние `exhausted` и событие `payments.dlq` сохраняются одной транзакцией. Publisher отправляет событие через `payments.dlx` и отмечает публикацию после подтверждения RabbitMQ; при сбое событие остаётся в outbox. Дубли завершённой обработки подтверждаются без новой записи для DLQ. Повторная публикация самого outbox по-прежнему возможна при падении между подтверждением брокера и коммитом БД.

Статус платежа описывает результат оплаты, а `attempt_state` — ход обработки сообщения и доставки webhook. Состояние попытки нужно, чтобы после падения consumer отличить прерванную обработку от запланированного повтора и уже доставленного уведомления: восстановить задержку, не расходовать лишнюю попытку и не отправлять завершённое уведомление заново.

Значения `attempt_state`: `ready` — до первого запуска, `processing` — попытка начата, `waiting_retry` — повтор запланирован, `delivered` — webhook доставлен, `exhausted` — попытки исчерпаны и передача в DLQ сохранена в outbox. Счётчик и `processing` сохраняются до начала обработки. Состояние `waiting_retry`, время `next_attempt_at` и событие outbox сохраняются одной транзакцией.

Если consumer прервался до сохранения повтора, следующая доставка восстанавливает его через outbox с задержкой 2 или 4 секунды, не начиная новую попытку. После третьей прерванной попытки сохраняются `exhausted` и событие outbox для DLQ. Заголовок `x-attempts` позволяет отличить запланированный повтор от старого дубля: старые сообщения подтверждаются без расходования попытки, а ранний повтор не начинает обработку до `next_attempt_at`.

Если результат платежа уже сохранён, повторяется только отправка webhook.
Статус `failed` — завершённый результат платежа, о котором также отправляется уведомление.
Ошибка доставки webhook и попадание сообщения в DLQ не меняют сохранённый статус платежа.

Сообщения с некорректным JSON, отсутствующим или невалидным `payment_id`, а также некорректным `x-attempts` сразу направляются через `payments.dlx` в `payments.dlq`. Заголовок `x-attempts`, если указан, должен быть целым числом от 0 до 3. В DLQ сохраняются исходное тело, заголовки и причина ошибки в `x-validation-error`. Исходное сообщение подтверждается только после подтверждённой передачи в DLQ.

Сообщение о несуществующем платеже или с номером повтора, несовместимым с состоянием платежа, передаётся в DLQ тем же способом. Временная ошибка БД или доставка повтора раньше срока возвращает сообщение в рабочую очередь.

Для нового платежа (`ready`) допустим только `x-attempts=0` или отсутствие заголовка. Ненулевое значение направляет сообщение в DLQ без изменения состояния и счётчика платежа; корректное исходное сообщение сможет начать первую попытку. Счётчик попыток берётся из БД, заголовок сообщения не увеличивает его.

## Тесты

```bash
docker compose -p payments-tests -f compose.test.yaml run --build --rm tests pytest
```

Тесты запускаются в Docker с отдельными PostgreSQL и RabbitMQ.

После завершения удалите тестовое окружение:

```bash
docker compose -p payments-tests -f compose.test.yaml down --volumes --remove-orphans
```
