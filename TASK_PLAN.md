# Разбиение на задачи

1. **Модели и БД** — настройки подключения, `payments`, `outbox`, первая миграция.
2. **API** — создание и получение платежа, API-ключ, идемпотентность, запись outbox в одной транзакции.
3. **Публикация outbox** — отправка событий в RabbitMQ.
4. **Consumer** — эмуляция платежа, сохранение результата, webhook, общий счётчик попыток и DLQ.
5. **Docker и README** — запуск всего сервиса и примеры запросов.

К каждой задаче добавляем нужные проверки. Одна задача — одна ветка.
После завершения вливаем ветку в `master`, следующую создаём от обновлённого `master`.

## Первая задача: модели и БД

1. **Настройки** — читать URL подключения к PostgreSQL из `.env`, добавить `.env.example`.
2. **Подключение к БД** — асинхронный engine и фабрика сессий SQLAlchemy.
3. **Модель `Payment`** — поля из ТЗ, уникальное ограничение на `idempotency_key`.
4. **Модель `Outbox`** — событие для публикации, дата создания и отметка об отправке.
5. **Alembic** — настроить миграции и создать первую для обеих таблиц.
6. **Проверка** — применить миграцию к PostgreSQL, проверить откат и повторное применение.

## Вторая задача: API

1. **Приложение** — создать FastAPI-приложение и зависимость для сессии БД.
2. **Аутентификация** — добавить API-ключ в настройки и `.env.example`, проверять `X-API-Key` на обоих эндпоинтах.
3. **Схемы** — описать запрос создания и ответы в Pydantic, добавить валидацию полей.
4. **Создание платежа** — `POST /api/v1/payments`: обязательный `Idempotency-Key`, платёж и outbox в одной транзакции, ответ `202 Accepted`.
5. **Идемпотентность** — при повторе с теми же данными возвращать существующий платёж, с другими — `409 Conflict`; учесть параллельные запросы.
6. **Получение платежа** — `GET /api/v1/payments/{payment_id}`: подробная информация или `404 Not Found`.
7. **Проверки** — по TDD покрыть аутентификацию, валидацию, создание и получение, повторы и параллельные запросы, откат транзакции при ошибке записи outbox.

## Третья задача: публикация outbox

1. **RabbitMQ** — добавить брокер в `compose.yaml`, URL подключения в настройки и `.env.example`.
2. **Подключение к брокеру** — настроить FastStream, устойчивую очередь `payments.new`, сохранение сообщений и подтверждения публикации от RabbitMQ.
3. **Выборка событий** — читать неопубликованные записи outbox порциями, блокируя выбранные строки, чтобы параллельные publisher не забирали одни и те же события.
4. **Публикация** — отправлять payload в `payments.new`, выставлять `published_at` только после подтверждения брокера. При ошибке оставлять событие для повторной отправки.
5. **Запуск publisher** — отдельный процесс с периодическим опросом outbox и корректным закрытием подключений при остановке.
6. **Проверки** — по TDD проверить успешную публикацию, повтор после ошибки и защиту от одновременной выборки одного события. Учесть, что сбой после отправки до сохранения `published_at` может привести к повторной доставке.

## Четвёртая задача: consumer

1. **Получение сообщений** — настроить FastStream-consumer для `payments.new`, разбирать payload с `payment_id`.
2. **Эмуляция платежа** — обработка за 2–5 секунд: 90% `succeeded`, 10% `failed`.
3. **Обработка платежа** — если платёж `pending`, вызвать эмуляцию и сохранить статус и дату обработки. Для `succeeded` и `failed` использовать сохранённый результат при отправке webhook, не вызывая эмуляцию повторно.
4. **Webhook** — после сохранения результата отправлять JSON с `payment_id` и `status` на URL платежа вне транзакции БД. Ответ `2xx` считать успешной доставкой; учитывать таймауты.
5. **Повторы и DLQ** — три попытки всего, с начала обработки сообщения, включая ошибки и падения consumer. Между попытками — экспоненциальная задержка; после исчерпания лимита — DLQ.

   Механизм задержки: две очереди ожидания с TTL и DLX для двух повторов с экспоненциальными задержками. После истечения TTL RabbitMQ возвращает сообщение в `payments.new`.

   Альтернативы:
   - PostgreSQL/outbox: сохранять повтор с временем отправки `available_at`; publisher раз в секунду публикует записи, время отправки которых наступило.
   - RabbitMQ 4.4: отложенная публикация через `x-opt-delivery-time` в quorum-очередь.
   - PostgreSQL с `LISTEN/NOTIFY` и таймером: ожидание ближайшего `available_at`, уведомление при добавлении более раннего задания; резервный опрос на случай потери уведомления.
   - Celery: готовая система фоновых задач с повторами, но добавляет второй механизм обработки рядом с FastStream.

6. **Подтверждение сообщения** — отправлять ACK после успешного webhook либо надёжной передачи сообщения на повтор или в DLQ.
7. **Запуск consumer** — отдельный процесс с корректным закрытием подключений к RabbitMQ, БД и HTTP-клиента при остановке.
8. **Проверки** — по TDD проверить обработку платежа, защиту от дублей, повтор только webhook при сохранённом результате, общий лимит попыток и попадание в DLQ. Проверить цепочку от создания платежа через API до получения webhook.
