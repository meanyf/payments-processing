# Контекст тестового задания

Источник: `Тестовое PYTHON .pdf` в корне проекта.

## Цель

Реализовать микросервис асинхронной обработки платежей: принять запрос,
обработать платёж через эмуляцию внешнего шлюза и уведомить клиента webhook.

## Стек

- FastAPI и Pydantic v2.
- SQLAlchemy 2.0 в асинхронном режиме, PostgreSQL.
- RabbitMQ и FastStream.
- Alembic, Docker и Docker Compose.

## Модель Payment

- Уникальный ID платежа.
- Сумма: decimal.
- Валюта: RUB, USD или EUR.
- Описание: строка; метаданные: JSON.
- Статус: pending, succeeded или failed.
- Уникальный idempotency key.
- Webhook URL.
- Даты создания и обработки.

## API

Все эндпоинты защищены статическим ключом в заголовке `X-API-Key`.

### POST /api/v1/payments

- Обязательный заголовок `Idempotency-Key`.
- Тело: сумма, валюта, описание, метаданные, webhook_url.
- Ответ: `202 Accepted`, payment_id, статус, created_at.
- При создании платежа событие публикуется в очередь `payments.new` через outbox.

### GET /api/v1/payments/{payment_id}

Возвращает детальную информацию о платеже.

## Асинхронная обработка

Один consumer выполняет все шаги:

1. Получает сообщение.
2. Эмулирует обработку за 2–5 секунд: 90% успеха, 10% ошибки.
3. Обновляет статус в БД.
4. Отправляет webhook на указанный URL.
5. Повторяет отправку при ошибках.

Требования: Outbox pattern, защита от дублей, 3 попытки с экспоненциальной
задержкой и Dead Letter Queue для окончательно необработанных сообщений.

## Результат

- Модели и миграции для таблиц `payments` и `outbox`.
- Два API-эндпоинта.
- Consumer, публикация outbox, retry и DLQ.
- Compose с сервисами postgres, rabbitmq, api, consumer.
- README с запуском и примерами.

Оцениваются архитектура и чистота кода, корректность outbox, работа с очередями,
обменниками и DLQ, идемпотентность, обработка ошибок и работоспособность Docker.

## Замечания к реализации

Это выводы из разбора, а не дополнительные явные требования PDF:

- Сохранять платёж и запись outbox в одной транзакции.
- Учитывать повторную публикацию outbox: consumer должен выдерживать дубли.
- При сбое webhook после обработки платежа повторять уведомление, не разыгрывая
  результат платежа заново.
- Защищать idempotency key уникальным ограничением БД, в том числе при
  параллельных запросах.

## Принятые решения

### Идемпотентность создания платежа

- Одинаковый ключ с другими данными запроса возвращает `409 Conflict`.

### Количество попыток

- 3 запуска всего: первый запуск и два повтора.
- Общий счётчик попыток обработки сообщения, включая отправку webhook.
- Попытка считается с начала обработки сообщения consumer’ом. Ошибка или падение consumer после начала обработки расходует попытку; недоставка сообщения consumer’у — нет.

### Формат payload webhook

- JSON с полями `payment_id` и `status` (`succeeded` или `failed`).

### Планирование повторов

- После первой и второй ошибки повтор сохраняется в outbox с `available_at` через 2 и 4 секунды. ACK следует после коммита. Publisher передаёт `x-attempts` из сохранённых заголовков.
- Ошибка публикации RabbitMQ оставляет событие в outbox и не расходует попытки consumer.
- После третьей ошибки сохраняется прямая передача через `payments.dlx` в `payments.dlq`.

### Тестовое окружение

- Полный набор тестов запускается через `docker compose -p payments-tests -f compose.test.yaml run --build --rm tests pytest`.
- Тестовые PostgreSQL и RabbitMQ доступны только внутри сети проекта, данные размещаются в tmpfs. После завершения ресурсы удаляются командой `docker compose -p payments-tests -f compose.test.yaml down --volumes --remove-orphans`.
- До импорта приложения `tests/conftest.py` заменяет подключения на `TEST_DATABASE_URL` и `TEST_RABBITMQ_URL`. Без этих переменных pytest останавливается; `.env` приложения не служит источником тестовых подключений.
